1 Introduction

This document lists C coding recommendations for use in the University of Canterbury Course ENCE260. It is a modified version of C/C++ guideline used in COSC208 in previous years, which in turn is a modified version of the Geotechnical Software Services document available at http://geosoft.no/styleguidelines.html, modified with permission. Most of the recommendations are common in the C/C++ development community, and are based on established standards collected from a number of sources, individual experience, local requirements/needs, as well as suggestions given in [1] - [4].

There are several reasons for introducing a new guideline rather than just referring to the ones above. The main reason is that these are far too general in their scope and that more specific rules (especially naming rules) need to be established. Also, the present guide has an annotated form that makes it far easier to use during project code reviews than most other existing guidelines. In addition, programming recommendations generally tend to mix style issues with language technical issues in a somewhat confusing manner. The present document does not contain any C technical recommendations at all, but focuses mainly on programming style.

While a given development environment (IDE) can improve the readability of code by access visibility, color coding, automatic formatting and so on, the programmer should never rely on such features. Source code should always be considered larger than the IDE it is developed within and should be written in a way that maximise its readability independent of any IDE.

1.1 Layout of the Recommendations.

The recommendations are grouped by topic and each recommendation is numbered to make it easier to refer to during reviews.

Layout of the recommendations is as follows:

0. GuidelineName: short description
Example if applicable
Motivation, background and additional information.

The motivation section is important. Coding standards and guidelines tend to start "religious wars", and it is important to state the background for the recommendation.

1.2 Recommendation Importance

In the guideline sections the terms must, should and can have special meaning. A must requirement must be followed, a should is a strong recommendation, and a can is a general guideline.

2 General Recommendations

1. Violations: any violation to these guidelines is allowed if it enhances readability.
The main goal of the recommendation is to improve readability and thereby the understanding and the maintainability and general quality of the code. It is impossible to cover all the specific cases in a general guide and the programmer should be flexible.

3 Naming Conventions

3.1 General Naming Conventions

2. General naming: all entities should be given names that communicate the entity's role to the reader.
cost, durationInSeconds, Employee, MAX_NUM_CHARS, setImageType()
This is the single most important naming rule. One-character identifiers must not be used except for the following situations:
  1. Generic temporary variables of basic types where there is a well-established convention, e.g., char c; char* s; int i;
  2. Variables that represent common physics measures that are conventionally represented with a single character, e.g., x and y for coordinates, t for generic time, v for generic velocity. However, l (el) should never be used for length or anything else, as it is difficult to distinguish from 1 (one) in most type fonts.
  3. In mathematical programs, when implementing a formula, e.g., discriminant = sqrt(b * b - 4 * a * c)
3. Type names: names representing types must be in mixed case starting with upper case.
Line, SavingsAccount
Common practice in the C/C++ development community.

4. Variable names: must be in mixed case starting with lower case.
line, savingsAccount
Common practice in the C/C++ development community. Makes variables easy to distinguish from types, and effectively resolves potential naming collision as in the declaration Line line;

5. Constant names: named constants must be all uppercase using underscore to separate words. This includes enumeration values and macros.
MAX_ITERATIONS, COLOR_RED, PI
Common practice in the C/C++ development community.

6. Function names: names representing functions must be in mixed case starting with lower case.
firstName(), computeTotalWidth()
Common practice in the C/C++ development community. This is identical to variable names, but functions in C are already distingushable from variables by their specific form.

7. Abbreviations: abbreviations and acronyms must not be uppercase when used in names [4].
exportHtmlSource(); // NOT: exportHTMLSource(); openDvdPlayer(); // NOT: openDVDPlayer();
Using all uppercase for the base name will give conflicts with the naming conventions given above. A variable of this type whould have to be named dVD, hTML etc., which is not very readable. Another problem is illustrated in the examples above: when the name is connected to another, the readability is seriously reduced; the word following the abbreviation does not stand out as it should.

8. Generic variables of user-defined types: should have the same name as their type.
void setTopic(Topic* topic) // NOT: void setTopic(Topic* value) // NOT: void setTopic(Topic* aTopic) // NOT: void setTopic(Topic* t) void connect(Database* database) // NOT: void connect(Database* db) // NOT: void connect (Database* oracleDB)
Obviously this convention cannot be used with built-in types like int which are reserved words.
Reduce complexity by reducing the number of terms and names used. Also makes it easy to deduce the type given a variable name only.

If for some reason this convention doesn't seem to fit it is a strong indication that the type name is badly chosen.

Non-generic variables have a role. These variables can often be named by combining role and type: 

  Point  startingPoint, centerPoint;
  Name   loginName;

9. Scope implications: shorter names can be used with variables having shorter scope. Variables with a large scope should have long names [1].
Scratch variables used for temporary storage or indices are best kept short. A programmer reading such variables should be able to assume that its value is not used outside of a few lines of code. Common scratch variables for integers are i, j, k and for characters c.

3.2 Specific Naming Conventions

10. Initialising: the term initialise (or initialize or init) can be used where an object or a concept is established.
initialiseFontSet();

11. GUI components: variables representing GUI components should be suffixed by the component type name.
mainWindow, propertiesDialog, widthScale, loginText, leftScrollbar, mainForm, fileMenu, minLabel, exitButton, yesToggle etc.
Enhances readability since the name gives the user an immediate clue of the type of the variable and thereby the object's resources.

12. Plurals: plural form should be used on names representing a collection of objects.
Point points[]; int values[];
Enhances readability since the name gives the user an immediate clue of the type of the variable and the operations that can be performed on its elements.

13. Cardinalities: the prefix n should be used for variables representing cardinalities of sets of objects.
nPoints, nLines
The notation is taken from mathematics where it is an established convention.

14. Entity identifiers: suffix No should be used for variables representing an entity number.
tableNo, employeeNo
The notation is taken from mathematics where it is an established convention for indicating an entity number.

Two alternative are the suffix Num or, in database contexts, the suffix Id: employeeNum, userId, itemId. A single convention should be used throughout, however.

15. Iterators: iterator variables should be called i, j, k etc.
for (int i = 0; i < nTables; i++) { ... }
The notation is taken from mathematics where it is an established convention for indicating iterators.

Variables named j, k etc. should be used for nested loops only.

16. Boolean names: the prefix is can usefully be used for boolean variables and functions.
isSet, isVisible, isFinished, isFound, isOpen
Common practice in the C/C++ development community.

Using the is prefix solves a common problem of choosing bad boolean names like status or flag. isStatus or isFlag simply doesn't fit, and the programmer is forced to choose more meaningful names.

There are a few alternatives to the is prefix that fit better in some situations, e.g. has, can and should: 

  bool hasLicense();
  bool canEvaluate();
  bool shouldSort();

17. Abbreviations: abbreviations in names should be avoided.
computeAverage(); // NOT: compAvg();
However, abbreviations are acceptable where they are widely used, and in fact are recommended where they are standard acronyms.

cmdis acceptable forcommand
initis acceptable forinitialise
  html  should be used rather than  HypertextMarkupLanguage  
cpushould be used rather thanCentralProcessingUnit

18. Negated booleans: negated boolean variable names must be avoided.
bool isError; // NOT: isNoError bool isFound; // NOT: isNotFound
The problem arises when such a name is used in conjunction with the logical negation operator as this results in a double negative. It is not immediately apparent what !isNotFound means.

19. Enumerations: enumeration constants can be prefixed by a common type name.
enum Colour { COLOUR_RED, COLOUR_GREEN, COLOUR_BLUE };
This gives additional information of where the declaration can be found, which constants belongs together, and what concept the constants represent.

Note also that the enum name typically should be singular as in enum Colour {...}. A plural name like enum Colours {...} may look fine when declaring the type, but it will look silly in use, particularly if you move to C++ where you find yourself writing things like Colours::RED rather than Colour::RED

20. Functions: functions should be named after what they return.
lastModifiedTime(...), maximumAge(...), rotationAngle(...)
Increase readability. Makes it clear what the unit should do.

21. Procedures: Procedures (void functions) should be named after what they do.
generateReport(...), readFile(...), updateCounts(...)
Increase readability. Makes it clear what the unit should do.

4 Files

4.1 Source Files

22. Header files: C header files should have the extension .h and source files the extension .c
These are the established C conventions.

23. Definitions: all definitions should reside in source files.
The header files should declare an interface, the source file should implement it. When looking for an implementation, the programmer should always know that it is found in the source file.

24. Struct declarations/definitions: give important structs their own files
Any non-trivial struct and its associated functions (which are effectively its methods) should be declared in a header file and defined in a source file, where the name of the files match the name of the struct.
student.h, student.c
Makes it easy to find the associated files of a given type.

25. Line length: file content must be kept within 80 columns.
80 columns is a common dimension for editors, terminal emulators, printers and debuggers, so ideally you should stay within that limit. Multiple source files can then be viewed side-by-side on screen. A further benefit from short lines is that they improve readability c.f. the use of columns of text in a newspaper.

26. Special characters: special characters like TAB and page break within source files must be avoided.
These characters are bound to cause problem for editors, printers, terminal emulators or debuggers when used in a multi-programmer, multi-platform environment.

27. Split lines: the incompleteness of split lines must be made obvious [1].
totalSum = a + b + c + d + e; functionCall (param1, param2, param3); setText ("Long line split " "into two parts."); for (tableNo = 0; tableNo < nTables; tableNo += tableStep) { ... }
Split lines occurs when a statement exceed the 80 column limit given above. It is difficult to give rigid rules for how lines should be split, but the examples above should give a general hint.

In general:

  • Break after a comma or an operator, and
  • Align the new line with the beginning of the expression on the previous line.

4.2 Include Files and Include Statements

28. Include guards: header files must contain an include guard.
#ifndef COM_COMPANY_MODULE_CLASSNAME_H #define COM_COMPANY_MODULE_CLASSNAME_H : #endif // COM_COMPANY_MODULE_CLASSNAME_H
The construction is to avoid compilation errors. The name convention resembles the location of the file inside the source tree and prevents naming conflicts.

29. Ordering includes: include statements should be sorted and grouped. Sort them by their hierarchical position in the system with low level files included first. Leave an empty line between groups of include statements.
#include <fstream> #include <iomanip> #include <qt/qbutton.h> #include <qt/qtextfield.h> #include "com/company/ui/PropertiesDialog.h" #include "com/company/ui/MainWindow.h"
In addition to show the reader the individual include files, it also give an immediate clue about the modules that are involved.

Include file paths must never be absolute. Compiler directives should instead be used to indicate root directories for includes.

30. Positioning includes: include statements must be located at the top of a file only.
Common practice. Avoid unwanted compilation side effects by "hidden" include statements deep into a source file.

5 Statements

5.1 Types

31. Local types: types that are local to one file only can be declared inside that file.
Enforces information hiding.

32. Explicit type conversions: type conversions must always be done explicitly. Never rely on implicit type conversion.
floatValue = (float) intValue; // NOT: floatValue = intValue;
By this, the programmer indicates that he/she is aware of the different types involved and that the mix is intentional.

5.2 Variables

33. Initialising variables: variables should be initialized when they are declared.
This ensures that variables are valid at any time and behaviour is deterministic.

34. Single meaning for variables: variables must never have dual meaning.
Enhance readability by ensuring all concepts are represented uniquely. Reduce chance of error by side effects.

35. Globals: use of global variables should be minimized.
Global variables reduce the portability of functions and increase the cognitive load on the reader (who has to search for the declaration and possibly other functions manipulating the variables to understand their roles fully. The contravene the rule of minimum scope, which is the goal of minimising the number of lines of code over which any identifier is visible. [See the Limiting Scope rule below.]

36. Implicit zero test: implicit test for 0 or NULL should not be used other than for boolean variables.
if (nLines != 0) // NOT: if (nLines) if (value != 0.0) // NOT: if (value) if (buffer != NULL) // NOT: if (buffer)
It is not necessarily defined by the C standard that ints and floats 0 are implemented as binary 0. Also, by using an explicit test the statement gives an immediate clue of the type being tested.

37. Limiting scope: variables should be declared in the smallest scope possible.
Keeping the operations on a variable within a small scope, it is easier to control the effects and side effects of the variable.

5.3 Loops

38. for loops: only loop control statements must be included in the for() construction.
sum = 0; // NOT: for (i = 0, sum = 0; i < 100; i++) { for (i = 0; i < 100; i++) { // sum += value[i]; sum += value[i]; // } }
Increase maintainability and readability. Make a clear distinction of what controls and what is contained in the loop.

39. Loop variable initialisation: loop variables should be initialised immediately before the loop.
isDone = false; // NOT: bool isDone = false; while (!isDone) { // ... ... // while (!isDone) { } // ... // }

40. Break and continue: the use of break and continue in loops should be minimised.
These statements should only be used if they give higher readability than their structured counterparts. Since programmers are inclined to use these statements out of laziness, alternatives should be investigated thoroughly. It is much harder to reason about whether the post-condition of a loop is satisfied if the loop body execution can be terminated prematurely.

41. Single return: functions should have a single return statement at the end.
return statements from within the body of a function should be avoided for the same reason as break and continue should be avoided within loops. One exception is recursive functions which often start with a test for a base case and return the simple solution in that case. Also, it is sometimes permissible to start a function with error checks and prematurely return with an error value in those cases.

5.4 Conditionals

42. Equality of booleans: do not write code that compares boolean expressions for equality with 1 or 0.
if (isReady and !isError) { ... } // NOT: if (isReady == 1 && isError == 0) { ... }
In ordinary speech we don't say things like "If it's raining is false I'll go for a walk", so why introduce this clumsy additional equality test into your programs? It just impedes readability or worse correctness, since values other than 1 may represent true.

43. Complex conditions: complex conditional expressions must be avoided. Introduce temporary boolean variables instead [1].
bool isFinished = (elementNo < 0) || (elementNo > maxElement); bool isRepeatedEntry = elementNo == lastElement; if (isFinished || isRepeatedEntry) { ... } // NOT: if ((elementNo < 0) || (elementNo > maxElement)|| elementNo == lastElement) { ... }
By assigning boolean variables to expressions, the program gets automatic documentation. The construction will be easier to read, debug and maintain.

44. Side-effects in expressions: executable statements in conditionals and loop conditions should be avoided.
File *fileHandle = open(fileName, "w"); if (!fileHandle) { ... } // NOT: if (!(fileHandle = open(fileName, "w"))) { ... }
Conditionals with executable statements are just very difficult to read. This is especially true for programmers new to C/C++.

An allowable exception is the common end-of-file or end-of-string idiom: 

while ((c = getchar()) != EOF) { ...

5.5 Miscellaneous

45. Literals: the use of magic numbers in the code should be avoided. Numbers other than 0 and 1 should be declared as named constants instead.
If the number does not have an obvious meaning by itself, the readability is enhanced by introducing a named constant instead.

46. Floating point literals: floating point literals should always be written with a decimal point and at least one digit before and after the point.
double total = 0.0; // NOT: double total = 0; double speed = 3.0e8; // NOT: double speed = 3e8; double fract = 0.5; // NOT: double fract = .5; double sum; ... sum = (a + b) * 10.0;
This emphasizes the different nature of integer and floating point numbers. Mathematically the two model completely different and non-compatible concepts.

Also, as in the last example above, it emphasizes the type of the assigned variable (sum) at a point in the code where this might not be evident.

47. Function return type: functions must always have the return type specified explicitly.
int getValue() // NOT: getValue() { ... }
If not explicitly specified, C/C++ assumes an int return value for functions. A programmer must never rely on this feature, since this might be confusing for programmers not aware of this artifact. Note too that the GNU C compiler will accept without warning a missing type for a function parameter, and assume int. This default must never be used.

48. Goto: goto should not be used.
Goto statements violate the idea of structured code. Only in some very few cases (for instance breaking out of deeply nested structures) should goto be considered, and only if the alternative structured counterpart is proven to be less readable.

6 Layout and Comments

6.1 Layout

49. Indentation amount: basic indentation should be 4.
for (i = 0; i < nElements; i++) { a[i] = 0; }
Indentation of 1 is too small to emphasize the logical layout of the code. Indentation larger than 4 makes deeply nested code difficult to read and increases the chance that the lines must be split. 2 and 4 are the more common, and 4 has been chosen because it produces a less cramped appearance.

50. Block layout: block layout should be as illustrated in example 1 below (recommended) or example 2, and must not be as shown in example 3 [4]. Function and class blocks must use the block layout of example 2.
while (!done) { doSomething(); done = moreToDo(); }
 while (!done) { doSomething(); done = moreToDo(); } while (!done) { doSomething(); done = moreToDo(); }
Example 3 introduces an extra indentation level which doesn't emphasize the logical structure of the code as clearly as examples 1 and 2.

51. if-else layout: the if-else class of statements should have the following form:
if (condition) { statements; } if (condition) { statements; } else { statements; } if (condition) { statements; } else if (condition) { statements; } else { statements; }

52. for layout: a for statement should have the following form:
for (initialization; condition; update) { statements; }
This follows from the general block rule above.

53. Empty statement: an empty for statement should have the following form:
for (initialization; condition; update) ;
This emphasizes the fact that the for statement is empty and it makes it obvious for the reader that this is intentional. Empty loops should be avoided however.

54. while layout: A while statement should have the following form:
while (condition) { statements; }
This follows from the general block rule above.

55. do-while layout: a do-while statement should have the following form:
do { statements; } while (condition);
This follows from the general block rule above.

56. switch layout: a switch statement should have the following form:
switch (condition) { case ABC : statements; /* Fallthrough */ case DEF : statements; break; case XYZ : statements; break; default : statements; break; }
Note that each case keyword is indented relative to the switch statement as a whole. This makes the entire switch statement stand out. Note also the extra space before the : character. The explicit Fallthrough comment should be included whenever there is a case statement without a break statement. Leaving the break out is a common error, and it must be made clear that it is intentional when it is not there.

57. Embedded statements: even single statement if-else, for or while statements should be written with braces.
if (condition) { statement; } while (condition) { statement; }
Use of braces in all cases produces a consistent-looking layout and allows extra statements to be added later without the risk of an omitted brace changing the meaning of the statement.

58. Depth of nesting: within a function, statements must not be nested more than three deep.
Nested structures are difficult to read and debug. The guideline allows for, say, an outer loop, an inner loop and an embedded if statement. Any logic more complicated than this should be simplified by use of support functions. For example, if processing an image by row then by column (which is already two levels of nesting), consider defining a function to compute each new pixel value, rather than embedding the per-pixel logic within the two nested loops.

59. Function size: no single function should be more than 40 lines long, including comments
It must be possible for the reader to study a function on the screen in its entirety without scrolling. Furthermore, good maintainable code requires that a problem be decomposed into small well-defined steps and a function more than 40 lines long is probably doing too much and needs further decomposition.

6.2 White Space

60. White space: use it!
- Conventional operators should be surrounded by a space character.
- C reserved words should be followed by a white space.
- Commas should be followed by a white space.
- Semicolons in for statments should be followed by a space character.
a = (b + c) * d; // NOT: a=(b+c)*d while (true) // NOT: while(true) { ... doSomething(a, b, c, d); // NOT: doSomething(a,b,c,d); for (i = 0; i < 10; i++) { // NOT: for(i=0;i<10;i++){ ...
Makes the individual components of the statements stand out. Enhances readability. It is difficult to give a complete list of the suggested use of whitespace in C/C++ code. The examples above however should give a general idea of the intentions.

61. Blank lines (a): logical units within a block should be separated by one blank line.
Matrix4x4 matrix; double cosAngle = cos(angle); double sinAngle = in(angle); setElement(&matrix, 1, 1, cosAngle); setElement(&1, 2, sinAngle); setElement(&2, 1, -sinAngle); setElement(&2, 2, cosAngle); multiply(matrix);
Enhance readability by introducing white space between logical units of a block.

62. Blank lines (b): functions should be separated by three blank lines.
By making the space larger than space within a function, the functions will stand out more clearly.

63. Variable alignment: variables in declarations can be left aligned.
AsciiFile *file; int nPoints; float x, y;
Enhance readability. The variables are easier to spot from the types by alignment.

64. Statement alignment: use alignment wherever it enhances readability.
value = (potential * oilDensity) / constant1 + (depth * waterDensity) / constant2 + (zCoordinateValue * gasDensity) / constant3; minPosition = computeDistance(min, x, y, z); averagePosition = computeDistance(average, x, y, z); switch (value) { case PHASE_OIL : strncpy(phase, "Oil", PHASE_BUFF_SIZE); break; case PHASE_WATER : strncpy(phase, "Water", PHASE_BUFF_SIZE); break; case PHASE_GAS : strncpy(phase, "Gas", PHASE_BUFF_SIZE); break; }
There are a number of places in the code where white space can be included to enhance readability even if this violates common guidelines. Many of these cases have to do with code alignment. General guidelines on code alignment are difficult to give, but the examples above should give a general clue.

6.3 Comments

65. Function comments: every function must have an explanatory comment. The comment should immediately precede the function signature.
The comment must explain what the function does, not how it does it. For functions that are part of the interface to a module, the comment should appear in the header file, not in the implementation file. The comment should not be replicated in the implementation, since redundancy is bad and it is likely that during maintenance the comments will not both be updated to match.
66. Tricky code: tricky code should not be commented but rewritten! [1]
In general, the use of comments should be minimized by making the code self-documenting by appropriate name choices and an explicit logical structure.
